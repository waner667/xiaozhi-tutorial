# 教程三 · 外设不工作怎么查（通用排查手册）

> ESP32 外设不出活的通用排查方法，与具体项目无关。
>
> **遇到任何反常现象，先来这一篇。** 不要急着换线或改代码。

这一篇里的每一条铁律都来自一次真实误判 ——
每一次都是"我先入为主地怀疑硬件，结论完全是反过来的"。

记在这里不是为了显得谨慎，是为了防止你重蹈覆辙。

---

## 症状速查

先按现象定位：

| 现象 | 先看哪几节 |
|---|---|
| 舵机通电有响声但不动 | [铁律三](#铁律三区分有阻力和收到有效信号) + [有电流还是没电流](#通电但不动的判据) |
| 舵机只动了一个 | [铁律五](#铁律五交换法定位物理层问题) |
| 按键完全没反应 | [铁律六](#铁律六接线之前先数清楚开关有几个脚) |
| OLED / I2C 设备一直黑 | [铁律一](#铁律一先打印启动基线电平) + 上面教程一的第 8 节 |
| 配好的固件突然不动了 | [铁律四](#铁律四先加调试固件再拆硬件) |
| 烧录连不上 / 一直等 | [烧录那一节](#二烧录) |
| 怀疑引脚被外设占了 | [铁律二](#铁律二gpio_get_level-读到低就是真的低) |

---

## 核心思想

> **加日志的成本极低，改变认知的成本极高。**
>
> 任何硬件问题，都应该先让固件自己把状态打印出来，
> **再动手碰任何一根线。**

## 一、五条铁律

### 铁律一：先打印启动基线电平

**上手第一件事**：给每个可疑引脚加一行上电即打印。

```cpp
ESP_LOGI(TAG, "  boot(GPIO9)=%d  touch(GPIO21)=%d  vol+(GPIO20)=%d  vol-(GPIO19)=%d",
         gpio_get_level(BOOT_BUTTON_GPIO), gpio_get_level(TOUCH_BUTTON_GPIO),
         gpio_get_level(VOLUME_UP_BUTTON_GPIO), gpio_get_level(VOLUME_DOWN_BUTTON_GPIO));
```

**为什么这是性价比最高的动作：**

- 一次烧录（几分钟）换来对所有引脚的确定性认知
- 不用问别人"按了有没有反应"，不用等对方配合
- 强到能直接排除掉一半的可能性

#### 判读表

| 启动电平 | 结论 |
|---|---|
| **1 / 0 混合** | **硬件问题，且只在 0 的那几个脚上。** 立刻排除固件。 |
| 全 0 | 全板短路，或所有引脚上电即被拉低 —— 查供电和面包板 |
| 全 1，按压无变化 | 线接错脚 / 开关不导通 / 引脚没配对 |
| 全 1，按压正常跳变 | 硬件没问题，去查回调注册和事件掩码 |

#### 为什么"1/0 混合"是最强信号

假设 BOOT 键读 1 而另外三路读 0：

```text
boot(GPIO9)=1  touch(GPIO21)=0  vol+(GPIO20)=0  vol-(GPIO19)=0
```

这一行直接告诉你三件事：

1. **固件是对的** —— 同一套配置代码，四个脚里有一个工作正常
2. **不是全局问题** —— 不是上拉没开、不是供电异常、不是烧录有问题
3. **范围精确到脚** —— 只需要看那三个 `0` 的脚上的元器件

有了已知正常的对照物（BOOT 键），问题从"整个板子怎么了"缩小成
"这三个元件怎么了"。

### 铁律二：`gpio_get_level()` 读到低就是真的低

**这条被违反过，而且代价不小。**

当时的怀疑链：ESP32-C6 的 USB Serial/JTAG 外设硬件固定挂在 GPIO18/19，
`sdkconfig` 里 `CONFIG_USJ_ENABLE_USB_SERIAL_JTAG=y` 是开的，
而按下的三个按键恰好读出低电平 —— 于是判定"外设抢走了引脚"。

**这个推断是错的。** 错在忽略了一个基本事实：

> **外设 claim 只改写输出路径（`gpio_set_level` 的信号路由），不改读路径。**

外设占用一个引脚只影响"你往里写什么"，
`gpio_get_level()` 读的仍然是**物理焊盘上的真实电平**。

所以：

```text
gpio_get_level() == 0   ⟹   这一脚在物理上确实被拉低了
```

不存在"被外设抢走导致读数异常"这种可能。

#### 怎么自己验证，不用背

**不需要相信任何人（包括文档作者），去源码里查：**

```bash
grep -i gpio esp-idf/components/esp_driver_usb_serial_jtag/src/usb_serial_jtag.c
```

一个 gpio claim 调用都没有 → 该外设从不碰引脚 → 推断当场作废。

> **推广**：任何"是不是被外设抢了"的怀疑，都可以用同样方法证伪。
> 查驱动源码是最快的，不是最权威的，但足够推翻一个假设。

---

### 铁律三：区分"有阻力"和"收到有效信号"

**误判案例**：用户说"舵机通电有阻力"。

当时的解读是"舵机已经通电了"，于是排除了供电问题，
把矛头指向共地和信号线 —— **方向偏了两小时。**

**"有阻力"证明不了什么。** 舵机齿轮本身就有摩擦阻力，手掰不动是正常的。

真正能证明信号被接收的是：

| 观察 | 证明什么 |
|---|---|
| **位移** —— 角度真的变了 | 确实收到有效指令 |
| **声音性质** —— 均匀低频保持音 vs 高频尖叫 | 后者是堵转 |
| **电流** —— 万用表能量到 mA 级 | 确实通电在做功 |

> **"通电有响声但不位移"是 PWM 无效的典型特征**，
> 而不是"信号基本正常只是不够强"。

---

#### 通电但不动的判据

```
设备有电 + 有机械阻力 + 完全不动
    │
    ├─ 先做最简单的物理判据
    │   万用表量 PWM 波形 / 看有没有明显电流
    │
    │   有电流但无位移 → 脉冲无效 → 优先怀疑软件（量纲、频率、占空比）
    │   无电流         → 优先怀疑硬件（供电、共地、接线）
    │
    └─ 纯软件 bug 会完美伪装成硬件故障
```

**本教程就有这么一例**：PWM 占空比的单位搞错了（把微秒当计数值传），
实际输出的脉冲只有 28.6µs，远低于舵机 500µs 的识别阈值。
表现是"有电、有阻力、滋滋响、纹丝不动" —— 和"信号线没接好"几乎无法从外部区分。

> **所以："有电 + 有响声 + 不动" → 先怀疑软件，不要先动硬件。**

---

### 铁律四：先加调试固件，再拆硬件

**一个带自动重试的诊断固件，节省的比一小时万用表试探多得多。**

具体做法：

1. **编译一个专用诊断固件** —— 把可疑引脚电平周期性打印，
   或者让外设按固定模式循环动作
2. **写一个带重试的烧录脚本**（下面有，120 秒窗口）
3. 一次烧录 + 一次串口监听，问题定位完毕

**为什么值得专门写重试脚本**：手动进下载模式（按住 BOOT）时，
人和脚本之间有调度延迟，窗口期经常对不上。

带重试的脚本把"按 BOOT 的时机"从一道**精确操作题**变成了
**"随便按，卡着点也没关系"**。

配套的还有**先开串口再触发复位**的监听脚本 —— 但有个坑：

> **开串口的瞬间如果 DTR/RTS 是默认高电平，会把板子复位掉，开机日志永久丢失。**
> 必须在 `serial.Serial()` 之前显式拉低：
>
> ```python
> ser = serial.Serial(port, baudrate, timeout=1)
> ser.setDTR(False)
> ser.setRTS(False)
> ```

**反过来更好用的做法是不依赖启动窗口**：如果代码里有周期性重试打印，
那纯监听就能抓到，不用赌复位时序。排查异步初始化问题时优先用这招。

---

### 铁律五：交换法定位物理层问题

当"某一路不动、其他路正常"时，**不要立刻改代码迁引脚**。先做一次**交换**：

```
把可疑的那路信号线，临时插到一个已知正常的引脚上
    │
    ├─ 动了   → 线 / 插孔 / 焊点的问题。硬件层，换根线或换个孔。
    └─ 不动   → 可能真是引脚被占用，或固件里这路没配置对
```

**实测**：接 GPIO18 的舵机不动，换到同一排另一个插孔就好了 ——
**面包板孔位接触不良**，不是外设占用。当时已经因为怀疑外设而改了代码迁到 GPIO14，
这次测试直接推翻了那个改动。

#### 面包板接触不良是头号故障源

孔位的夹持力会随插拔次数衰减。所以：

- **"某一路完全不动 + 软件配置全对" → 优先怀疑插孔，而不是引脚被占用**
- 验证成本极低：换同排另一个孔，十几秒出结果
- 代价：下次再遇到同样的故障，你已经知道要先换孔了

**在改代码迁引脚之前，一定要先做这一步。**

### 铁律六：接线之前先数清楚开关有几个脚

**微动开关的脚数直接决定接法，两脚和三脚的结构完全不同。**

这是"按键完全没反应"的最高频根因，而且症状极具迷惑性。

#### 二脚 / 四脚

机身**同侧的两个脚内部导通**，两侧各成一组 → 本质就是普通单刀单掷开关。

"一头接 GPIO、一头接 GND"即可，怎么插都行。

#### 三脚

引脚排列 `A | B | C`，**两个外侧脚（A 和 C）内部属同一端**，
**中间脚（B）是另一端**。很多型号还内置指示灯（多一个脚）。

**陷阱**：用二脚的思路去接三脚，很可能把"同侧两脚"误当成"一端两脚"，
结果是把**同一个端子接到自己身上**。于是开关永远闭合不到 GND，
GPIO 悬空（或被读成一直低），按键彻底没反应。

**正确接法：中间脚接一侧，外侧任一脚接另一侧。**

#### 为什么症状像固件 bug

配置是 `active_level = 0` + 内部上拉，这是**完全正确**的配置。

一个一直读低的引脚，在这个配置下看起来就像"从开机就一直被按住"：

1. 初始化时引脚已经是"按下"状态 → **永远不会有按下沿**
2. 大约 1~2 秒后触发一次长按回调
3. 之后电平再不变 → 再无任何事件

**指纹特征：开机有一次事件，按压时零事件。**

#### 和"极性"是同一件事

- 芯片内部上拉让引脚**平时是高电平**（松开）
- 按下把引脚接到 **GND** → **低电平**

所以恒低不是"按键坏了"，而是**两极被接成了同一个电位**，
"按下"这个状态从一开始就一直是成立的。

### 铁律七（补充）：选引脚前先查禁区

ESP32-C6 有几类绝对不能乱用的脚：

| 引脚 | 原因 | 后果 |
|---|---|---|
| `GPIO24` ~ `GPIO30` | 芯片内部 SPI flash | **启动即失败，无任何补救** |
| `GPIO16` / `GPIO17` | UART0，默认串口日志 | 烧录失败 / 看不到日志 |
| `GPIO8` | strapping（SPI boot） | 上电电平决定启动模式，可能变砖 |
| `GPIO0` | strapping（下载模式） | 上电电平决定是否进下载模式 |

**strapping 是什么意思**：芯片上电瞬间会采样这几个引脚的电平来决定启动模式。
你在运行期把功能配上去没问题，但**复位瞬间的电平**决定了它能不能正常启动。

> **绝对不要在 GPIO0 / GPIO8 上挂会被拉低的负载。**

### 引脚定义的单一来源

把板级引脚定义集中在一个文件里：

```c
#define SERVO_GPIO_RF GPIO_NUM_3   // 舵机1 右前腿
#define SERVO_GPIO_RB GPIO_NUM_18  // 舵机2 右后腿
#define SERVO_GPIO_LF GPIO_NUM_22  // 舵机3 左前腿
#define SERVO_GPIO_LB GPIO_NUM_23  // 舵机4 左后腿
```

好处：

- 换脚只改一处
- 排查时直接 grep 这个文件，确认某个脚有没有被别人用
- 注释里能留下"当初为什么选这个脚"的决策依据

**还应该在这个文件里留排查记录**：

```c
// ★ 排查留档：舵机2(GPIO18) 最初完全不动，一度怀疑是 ESP32-C6 的
//   USB Serial/JTAG 外设占用。但把面包板插孔换到同排另一个孔后
//   舵机就动了 → 实为面包板孔接触不良，GPIO18 保留不变。
//   若日后该路又不动，可先换插孔/换杜邦线，再考虑迁脚。
```

> **这段注释的价值超过一百行代码。**
> 它让三个月后的自己（或同事）不会重新怀疑一遍已经排除过的方向，
> 也不会贸然改脚。

## 二、烧录

### 2.1 串口识别：不要相信 COM 号

**COM 号会变。** 同一个板子插拔几次就可能换一个号。**认芯片的 VID:PID**：

```python
from serial.tools import list_ports
for p in list_ports.comports():
    print(p.device, '|', p.description, '|', p.hwid)
```

识别到的输出长这样（COM 号每次可能不同，看 VID:PID）：

```text
<COM> | USB-Enhanced-SERIAL CH343 | USB VID:PID=1A86:55D3
```

> **注意：CH340 和 CH343 都是南京沁恒的芯片，驱动不同但都要手动进下载模式。**
> 网上大量教程写的是 CH340，如果你的板子是 CH343，别被误导。

**判据：拔掉板子再列一次，对比少了哪个。**

> **Windows 上 COM3/4/5/6/8/9 这类通常是蓝牙虚拟口。**
> 往这些口烧录，esptool 会**安静地空等，然后超时** —— 看起来像板子坏了，其实只是选错口。

### 2.2 进入下载模式

**C6 的自动复位在 CH343 上不工作**，`--before default_reset` 无效。

必须手动：

```
1. 按住 BOOT 键 不放
2. 点一下 RST 键
3. 松开 RST
4. 继续按住 BOOT 约 2 秒
5. 松开 BOOT
```

**最稳的做法**：先按住 BOOT，再点 RST，然后等 2 秒松 BOOT。

### 2.3 ★ 必须单次连接烧录

**这是最关键的烧录坑。**

**错误做法**：

```bash
esptool chip-id                    # ❌ 第一步：探测
esptool write-flash ...            # ❌ 第二步：烧录
```

第一次探测结束时会执行一次 `hard_reset`，**把板子踢回正常固件**。
第二次就再也连不上了：

```text
No serial data received
```

**正确做法**：

```bash
esptool --chip esp32c6 --port <COM> \
        --before no-reset --after no-reset \
        write-flash --flash-mode dio --flash-size 16MB --flash-freq 80m \
        0x0 bootloader.bin 0x8000 partition-table.bin ...
```

`--after no-reset` 让芯片停在 stub 状态，烧完再单独复位：

```bash
esptool --chip esp32c6 --port <COM> run
```

### 2.4 烧录偏移从哪来

**不要手抄。** 从编译产物里读：

```
build/flasher_args.json
```

ESP32-C6 + 16MB Flash 的实际值：

| 偏移 | 文件 |
|---|---|
| `0x0` | `build/bootloader/bootloader.bin` |
| `0x8000` | `build/partition_table/partition-table.bin` |
| `0xd000` | `build/ota_data_initial.bin` |
| `0x20000` | `build/xiaozhi.bin` |
| `0x800000` | `build/generated_assets.bin` |

参数：`dio` / `16MB` / `80m` / 波特率 `460800`

### 2.5 esptool 5.x 语法坑

```bash
# ✅ 正确：--baud 是全局选项，必须在 write-flash 之前
#         --flash-* 是子命令选项，必须在 write-flash 之后
esptool --chip esp32c6 --port <COM> --baud 460800 write-flash \
        --flash-mode dio --flash-size 16MB --flash-freq 80m \
        0x0 bootloader.bin ...
```

| 写错的形式 | 报错 |
|---|---|
| `--baud` 放在 `write-flash` 后面 | `No such option '--baud'` |
| `--flash-mode` 放在 `write-flash` 前面 | `No such option '--flash-mode'` |
| `chip_id` | 已废弃，用 `chip-id` |

> **不要用 PlatformIO 自带的 `tool-esptool`。** 它是 2014 年的 esptool-ck v0.4.13，
> **不支持 ESP32-C6**。用 ESP-IDF 的 venv 里那个新版 esptool。

### 2.6 完整烧录脚本（含 120 秒重试）

```python
#!/usr/bin/env python
"""ESP32-C6 单次连接烧录，带 120 秒下载模式重试窗口。"""
import subprocess, sys, time, os, json

ESPTOOL = os.environ.get('ESPTOOL', 'esptool')
BUILD   = os.environ.get('BUILD_DIR', 'build')
PORT    = os.environ['SERIAL_PORT']        # 先用 list_ports 认出真正的板子那个口

# 偏移不要手抄，从 flasher_args.json 读
with open(os.path.join(BUILD, 'flasher_args.json'), encoding='utf-8') as f:
    fa = json.load(f)
FILES = [(int(x['offset'], 16) if isinstance(x['offset'], str) else x['offset'],
          os.path.join(BUILD, x['file'])) for x in fa['flash_files']]

args = [ESPTOOL, '--chip', 'esp32c6', '--port', PORT,
        '--baud', '460800',
        '--before', 'no-reset', '--after', 'no-reset', 'write-flash',
        '--flash-mode', fa['flash_mode'], '--flash-size', fa['flash_size'],
        '--flash-freq', fa['flash_freq']]
for off, path in FILES:
    args += [hex(off), path]

for attempt in range(40):            # 40 × 3s = 120 秒窗口
    print(f"=== attempt {attempt+1}/40 ===", flush=True)
    r = subprocess.run(args, capture_output=True, text=True, errors='replace')
    if 'Hash of data verified' in (r.stdout or '') + (r.stderr or ''):
        print("FLASH_OK")
        subprocess.run([ESPTOOL, '--chip', 'esp32c6', '--port', PORT, 'run'])
        sys.exit(0)
    time.sleep(3)

print("FLASH_FAILED：120 秒内没进下载模式")
sys.exit(1)
```

**这个脚本的核心价值**：让"按 BOOT 的时机"不再重要。
随便按，卡着点也没关系，脚本会一直重试。

## 三、面包板与供电

### 3.1 面包板的电气规则

**同一排（同一横排）的 5 个孔内部是导通的** —— 这就是所谓的"轨"。

后果：

- GPIO 信号线和 GND 线落在同一排 → **短路**，引脚恒为低电平
- 一根线插歪到相邻排 → 静默短路，现象和"没插紧"极像

**好消息**：开关横跨中缝插是对的。开关的两脚落在中缝两侧，天然落在不同的排上。

**电源轨中间有断口。** 长条形的红色/蓝色标线看着连成一条，
其实**左右两半是分开的** —— 新手最常忽略这一点。

**载流上限约 1A。** 面包板的接触电阻比导线大得多，
舵机那种 2A 级负载**绝对不能全走面包板电源轨**。

### 3.2 排查供电问题的顺序

```
1. 画供电拓扑图 —— 谁给谁供电，一眼看清
   ↓
2. 万用表量主控芯片的 VCC（应为 3.0~3.4V）
   0V → 主控没供电，往上游查
   ↓
3. 量负载的红线（舵机应为 ~5V）
   正常但不动 → 不是供电问题，查共地/信号/PWM
   ↓
4. 量负载动作期间的电压跌落
   明显跌落 → 电源容量不足或缺退耦电容
```

> **"插上 USB 就好，不插就不显示"这类现象，第一反应应该是画拓扑图，
> 而不是查驱动代码。**

### 3.3 万用表量测口诀

新手最容易混淆两件事：**断电还是上电、用哪个档**。

**断电 → Ω 电阻档**，量 SDA/SCK 对 GND：

| 读数 | 含义 |
|---|---|
| `∞` / `OL` | 正常（高阻） |
| 几 kΩ | 正常（内部上拉） |
| **0 或接近 0** | **短路** |

**上电 → V⎓ 直流档**，量电平：

| 读数 | 含义 |
|---|---|
| `3.0 ~ 3.4 V` | 正常 |
| **0V** | 有问题 |
| `~0.6 V` | **ESD 保护二极管钳位** → 说明屏侧 VCC 没接通 |

**两条硬规矩：**

1. **断电量电压永远是 0V，完全没有意义。**
2. 读到什么 `0.6V` 左右，不是"信号弱"，是**被钳位了**，说明供电没到。

### 3.4 布线规范

**分支独立，不要共用电源轨：**

```
✗ 错误：舵机红线和 ESP32 都从面包板电源轨取电
        → 峰值时轨上压降大，ESP32 跟着掉压

✓ 正确：舵机粗线直连电源正极（不经面包板）
        ESP32 从电源的另一路分支走
        两条分支只在"电源负极"汇合（共地点）
```

**GND 用一根专线**，比"每根 GND 都插到公共轨"更可靠：

```
所有 GND（电源负极、各负载棕线、ESP32）→ 汇到一处 → 一根粗线到 ESP32 GND
```

好处：GND 路径唯一、接触点从"杜邦头 + 面包板孔"减少到"杜邦头"、
以后拔插单根信号线不会影响其他设备。

**把信号和电源分开走。** 舵机信号线和按键信号线在同一片区域交叉走线时，
插错孔的概率很高。**分区域走线。**

## 四、固件回退：走 git，不要走 read_flash

### read_flash 为什么不可靠

实测把这条路试穿了：

- 全片 4MB 读取**极不稳定**，串口丢字节
- 分块最多稳定读到约 **2MB**
- 最终只备份到 1,998,848 字节（0x1E8000），
  **不含 bootloader 和分区表**，只能作应急参考

### git 是正解

源码基线只要一个 tag：

```bash
# 项目开始前先存档
git add -A && git commit -m "baseline: <当前可用状态>"
git tag <baseline-name>

# 改坏了要回退
git checkout <baseline-name>
idf.py build
# 然后烧录
```

**这条路是确定性的**，而且回退的是完整的、可修改的源码，
比一个二进制镜像有用得多。

### 开项目时的标准动作

```bash
# 1. 建立基线
git add -A && git commit -m "baseline: <当前可用状态>"
git tag <baseline-name>

# 2. 开开发分支
git checkout -b <feature-name>

# 3. 记下 tag 名，写进项目 README
```

**第 3 步最容易被跳过，也最致命** ——
三个月后你不会记得基线 tag 叫什么，回退就成了不可能的任务。

## 六、排查顺序总表

遇到"某个外设不工作"，**按这个顺序走，不要跳步**：

```
1. 加打印，把物理状态读出来
   └─ 一次烧录换来确定性认知，成本最低        [铁律一]

2. 查驱动源码，证伪"被外设占用"
   └─ grep gpio，不相信任何未经验证的推断      [铁律二]

3. 做物理判据，区分软件 / 硬件
   └─ 量电流、量波形、看是否真有位移            [铁律三]

4. 交换法定位物理层
   └─ 换插孔、换引脚、换根线                   [铁律五]

5. 最后才改代码迁引脚
   └─ 前面四步没做就改代码，等于蒙眼改
```

## 七、反面教材汇总

**下面每一次，都是我先怀疑硬件，结论完全反过来。**
列出来是为了让每一条都变成你的经验：

| # | 曾经的假设 | 实际情况 | 靠什么推翻的 |
|---|---|---|---|
| 1 | GPIO19/20 被 USB Serial/JTAG 占用 | 驱动源码里一个 gpio claim 都没有 | grep 源码 |
| 2 | GPIO18 被 USB Serial/JTAG 占用 | 面包板插孔接触不良，换孔就好 | 换插孔 |
| 3 | 按键线插进了 GND 导轨 | 三脚开关按二脚接法，同端短接自己 | 数开关脚数 |
| 4 | 舵机不动 = 共地没接 / 信号线接错 | PWM 占空比单位错，实际脉冲 28.6µs | 加自动循环固件看输出 |
| 5 | "有阻力"说明舵机已通电 | 齿轮摩擦阻力而已，什么都证明不了 | 看是否真有位移 |
| 6 | 供电不稳导致崩溃 | 崩溃点每次固定在同一行 | 栈回溯 |
| 7 | 板子烧坏了 | 能播报、联网、激活、屏能亮 | 功能实测 |
| 8 | I2C 地址是 0x3D | 真实地址 0x3C，0x3D 是钳位假象 | 多轮探测 |

**共同点：每一次都在还没获得物理事实之前就下结论，然后引导去改硬件。**

> **工具和耐心应该花在获取事实上，而不是说服对方重接线。**
>
> 上面 8 次里有 4 次代价是拆装硬件。而推翻每一条只需要一行日志或一次测量。
